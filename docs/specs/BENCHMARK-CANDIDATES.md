# Benchmark Candidates

The bench-side lifecycle of a Benchmark Candidate: how a candidate is promoted from the operator's private Config Repo into the public `candidates/` tree, how runs of it are queued and executed by the batch scheduler, and how its results are published.

## Context

Issue #39 rules that a Benchmark Candidate **is** a TheOzolith worker-type definition, exchanged as a Candidate Bundle whose identity the bench recomputes and never trusts ([BENCH-CONTRACT.md](BENCH-CONTRACT.md) owns the bundle format, the identity spec, and the Run Contract; `silverquillm.candidate` is the bench's ingestion). Around that contract the bench owns three surfaces of its own (#39 §§4–5): the curated public set and its promote gate, the file-backed batch queue with its single-writer scheduler, and the publish gate that ports results into the public tree. Nothing here is load-bearing for the substrate — it learns nothing about batches, promotion, or publishing.

Three invariants run through every surface: everything under `candidates/`, `batches/` and `published/` is public, so no secret value and no host-local detail may enter it; the promote and publish scripts and the scheduler are git-agnostic — they write tracked files but never run git, and the operator's commit is the approval stamp; and a partially failed operation is always recoverable without silently continuing in an ambiguous state.

## Design

### The curated candidates tree

`candidates/` is the public, curated set of Benchmark Candidates this repo ships — flat and deduplicating, one directory per identity:

```
candidates/<slug>--<hash8>/
  README.md                        what the candidate is and what it varies
  source/worker-types/<type>.toml  the definition the bundle was exported from, base pinned by digest
  source/knowledge/<name>/         the referenced knowledge SOURCE tree (when the candidate bakes one)
  source/policy/<name>/            the referenced Agent Policy tree (when the candidate bakes one)
  bundle/                          the Candidate Bundle, verified as-is on every run
```

`<hash8>` is the first eight characters of the Candidate Hash recomputed from `bundle/` (CONTEXT.md → Candidate Hash). The directory name is a recorded value: `silverquillm run --candidate` and the platform test `tests/test_reference_candidates.py` recompute the identity on every run and refuse a directory whose suffix disagrees with its bundle. The platform test holds every checked-in candidate to the same bar: it ingests, carries its recomputed hash8, holds secret slot *names* only across the **whole** directory (README, vendored definition, knowledge and policy source, the `PUBLISHABLE` marker — scanned with the production credential detector, `silverquillm.candidate.scan_tree_for_credentials`), documents its identity in a completed README, re-exports byte for byte from `source/` with no registry access, and — when it bakes knowledge — vendors a source tree that carries its publishable declaration. The vanilla Reference Candidates additionally vary nothing.

### Promotion — vendor-at-promote is strict

`scripts/promote_candidate.py <config-repo> <worker-type> [--slug NAME] [--candidates-dir DIR] [--docker-config DIR] [--dry-run]` copies one definition from the operator's private Config Repo (the-ozolith ADR-0048 shape: `worker-types/` + `knowledge/` + `policy/`) into `candidates/`. It never runs git: the operator reviews the new directory and commits it, and that commit is the approval stamp.

| Step | Rule |
| --- | --- |
| Publishability gate | A knowledge tree the definition references (`knowledge = "knowledge/<name>"`) must exist in the Config Repo **and** carry a regular file named `PUBLISHABLE` at its root — the operator's explicit declaration (its text is the basis, e.g. the license). TheOzolith's knowledge loader ignores the file and the compiled tree never contains it, so the marker moves no pin and no identity. A missing tree or a missing marker is a hard refusal naming the rule: **knowledge that cannot be published means the candidate cannot be promoted and its results cannot be published**. A referenced Agent Policy tree must exist (it is vendored the same way). |
| Export | The bundle is exported by TheOzolith's own tooling (`theozolith_control.candidate.export_candidate`) into a private staging directory beside the destination, then ingested through the bench's own path (`load_candidate_bundle`: verifier, recomputed identity, secret-value refusal over the bundle). A private base tag resolves through `--docker-config`; the credential never enters the bundle. |
| Name | `candidates/<slug>--<hash8>/`, slug defaulting to the worker-type name. |
| Vendored source | The definition is copied with its top-level `base` pinned to the digest the export resolved when the source carried the tag only (the one edit; a digest-pinned source is copied verbatim). The referenced knowledge and policy source trees are copied whole — regular files and directories only; symlinks, special files and unreadable files refuse; `.git`, `__pycache__`, `.DS_Store` and bytecode are left out. |
| Dedup by identity — source-aware | The same identity already promoted under this name is a no-op **only** when the existing copy is whole and equivalent: its bundle verifies and recomputes to the identity, re-exporting its `source/` with its own recorded `exported_at` reproduces its `bundle/` byte for byte, and its `source/` equals the source being promoted byte for byte (bytes and exec bits; the `PUBLISHABLE` marker and policy source included). The README is the operator's to complete and maintain and is never compared. A missing, tampered or irreproducible existing source, a source that differs (same identity, different source is a conflict), a bundle that does not recompute to this identity, or the same identity under another slug is a refusal that leaves the existing directory untouched. A later export with a new `exported_at` but the same identity and source stays a no-op. |
| Reproducibility proof | Before anything is published, `source/` is re-exported with the recorded `exported_at` and must reproduce `bundle/` byte for byte; an irreproducible copy is refused. |
| README stub | Written with the identity table, provenance, and `TODO(promote)` placeholders for what the candidate varies, where the base digest came from, and — optionally — a safe repository label and revision for the Config Repo. It names no host-local path: the source is "the operator's Config Repo". The platform test refuses a checked-in README that still carries the placeholder. |
| No host-local paths | The files promotion generates (the README stub, the vendored definition) may name neither the Config Repo's absolute path, nor the home directory, nor the Docker config directory; no vendored file may name the Config Repo's absolute path. A hit refuses, naming the file and the *kind* of path (diagnostics may name local paths; generated artifacts never do). |
| Whole-tree secret scan | Last, after every file is staged, the complete staging directory — `bundle/`, `source/worker-types/`, all knowledge source including `PUBLISHABLE`, all policy source, the README — is scanned with the production credential detector (Anthropic and OpenAI keys, classic and fine-grained GitHub tokens, AWS access-key ids, Slack tokens, private-key blocks, JWTs, bearer credentials, a declared secret slot used as an assignment key with a non-empty value). Declared-slot assignment detection is **not** length- or character-set-limited: the key may be quoted, the operator is `=` or `:`, and any non-empty scalar — `SLOT=x`, `SLOT = "short"`, `SLOT: opaque/+value==`, `"SLOT": "…"`, `'SLOT' = 'value with spaces'`, a placeholder in angle brackets — is a value; a bare value reaches to the end of its line, a quoted one to its closing quote — inside a quoted value a backslash escapes the next character, so an escaped quote or backslash (`\"`, `\\`, the way JSON and every serializer that emits it write a value that contains a quote) belongs to the value and the string closes only at an unescaped quote, while a quote that never closes falls through to the bare form and the line goes whole; no fragment of an assigned value survives redaction. An empty assignment (`SLOT=`, `SLOT = ""` — the vendored definition's own `[secrets]` table declares slots this way), a declaration list (`"secret_slots": ["SLOT"]`) and prose that merely names the slot are not values. Bytes are matched as bytes, so a binary file is scanned like any other; an unreadable file refuses. A hit refuses naming the file and the shape, never the value. |
| Atomicity | Every check runs in staging; the candidate directory appears through one rename at the end. A refusal leaves `candidates/` untouched. |
| Cleanup | The slug is validated (one safe path segment without `--`) before anything is staged. Staging sits beside the destination — same filesystem, so the final rename is atomic — and is removed strictly after a refusal or a dry run, never with errors ignored, because it may hold the very content promotion refused, a rejected credential value included. A `candidates/` directory this invocation created — and any missing ancestor made with it — is removed again when it is left empty, and only on proof (`silverquillm.created_directories`): each is created descriptor-first (made under a private name, opened, its identity taken from that descriptor) and placed with a no-replace rename under an advisory `flock` on its parent directory, so the identity never comes from a pathname and a directory that appears under the name meanwhile is someone else's, used as found and never removed; each is removed only while proven, under that same lock, still to be the very directory created and empty, and through a private name again, so the one deletion is of a name nobody else knows and a replacement caught in that instant is moved back and kept. A refusal or dry run thus preserves the pre-invocation tree exactly (existence, entries, bytes, mtimes), and every failure after the directory was created — opening it, creating staging inside it — unwinds the same way before the refusal is reported. When staging cannot be removed, or a created directory cannot be inspected or removed, is no longer the one promotion made, is no longer empty, or could not be moved back into place, promotion raises `PromotionCleanupError` instead of reporting a clean refusal: it names the retained path — `candidates/.promote-<slug>-<nonce>/` (never its bytes), or the directory itself — states that the "nothing written" guarantee was not met, attaches the refusal that preceded it, and the CLI prints both and exits 2; exit 1 is reported only over a restored tree. The parent-directory lock serializes every promote and publish invocation, leaves no artifact, and is what closes both instants against them; on a platform without `RENAME_NOREPLACE` (Linux before 3.15, a C library without `renameat2`) the placement is a plain rename, safe under that lock alone. The operator inspects and removes a retained staging tree by hand; the repository ignores `candidates/.promote-*` so it can never be committed by accident. |

### The batch queue and the scheduler

The queue is the directory `batches/`. A **Batch** is one file `batches/<id>.toml` — desired state, authored and edited in `$EDITOR`, never written by the scheduler:

```toml
not_before = 2026-09-04T02:00:00Z      # optional; RFC 3339 with an offset

[[runs]]
candidate = "candidates/vanilla-claude--4e8b75b6"   # a path, or a candidates/ entry name
mode = "basic"
benchmark = "smoke"
budget_seconds = 14400
```

Exactly these keys, strictly: an unknown key, a naive `not_before`, or a non-positive budget makes the file malformed. A malformed batch is skipped loudly (reported once per file version to the scheduler log) and surfaced by `queue ls`. **Batch ids are permanent, one-shot identifiers**: the committed state file is the record of what ran under that id, so an id is never reused for an unrelated batch — write a new file.

Three kinds of file sit beside the batch files:

| File | Tracked? | Contents |
| --- | --- | --- |
| `batches/state/<id>.json` | **Committed** — portable observed state; the operator commits checkpoints | `schema_version`, `batch`, `batch_file` (the file *name*), `updated_at`, and one entry per *started* run: `index`, the `spec` as consumed, `state` (`running` → `done` / `failed`), `run_id`, `candidate_hash`, `hash8`, the recomputed `identity`, portable timestamps (`started_at`, `resolved_at`, `finished_at`), `ok`, `failure_class`, a one-line `summary` and a sanitized `error`. The number of entries is the batch's cursor. The consumed `spec` keeps a relative candidate reference verbatim and records an absolute one only as the label `<external-candidate>/<basename>`: the recorded identity is the authoritative account of what ran, and a pending entry always resolves from the batch file, never from this copy. Never: an absolute candidate or run path, a username or home directory, a pid or hostname, container data, an environment value, a raw traceback or exception text that could carry a secret — every summary and error is redacted first (the exact values bound to the bundle's declared secret slots in the effective environment, whatever their shape; a value assigned to one of those slots; every generic credential shape; then known roots become `<repo>`, `<runs>`, `<results-repo>`, `<batches>`, `<home>`, `<tmp>`). Every scheduler log line passes the same redaction on its one way to the sink: the generic shapes and root placeholders always — blocked and malformed warnings, acknowledgements, recovery, the serve line (which names the queue as `<batches>`, never by absolute path) — and, once a run has resolved its bundle, the exact bound values of its declared slots too (`STARTED`, `DONE`/`FAILED`, executor errors, interruptions). Identity fields (run id, worker type, candidate hash) are recorded verbatim in the state and, in the log, redacted by value like any other text. **Read as strictly as written:** every top-level field is required — `batch` a plain id (`[A-Za-z0-9][A-Za-z0-9._-]*`, also enforced on the batch file's name at parse time), `batch_file` exactly `<id>.toml`, `updated_at` the scheduler's own UTC stamp (`YYYY-MM-DDThh:mm:ss+00:00`) — and so is every run field, with the type and shape the scheduler writes: a whole `spec` (all four keys, non-empty one-line strings, a positive integer budget, no absolute path, no unknown key), canonical timestamps, a plain run id, a 64-hex `candidate_hash` with its `hash8`, an `identity` that re-validates as an `ozolith-v1` identity hashing to it, `ok` a boolean or null, `failure_class` a plain token or null, one-line capped `summary` and `error`. The entry must be lifecycle-coherent: `pending` is never persisted (the list is the cursor of *started* runs) and is refused; a `running` run carries its identity (run id, hash, hash8, identity, `resolved_at` together) and no outcome; a `done` run carries its identity, `finished_at`, `ok: true` and neither failure class nor error; a `failed` run carries `finished_at`, `ok: false` and a failure class, and carries its identity unless — and only unless — the class is `unresolvable` (a run id is assigned only when the spec resolves). The run list as a whole must be a sequence the serial scheduler can produce: at most one `running` entry, and only as the last — the scheduler starts a run only once the previous one finished, so a `done` or `failed` entry after a `running` one would be a cursor advanced past a run that never finished, and `[running, done]` is refused whole (never reordered or repaired) even though each entry is coherent on its own. Anything less is a `StateError`: the batch is blocked (`unreadable-state`), its cursor does not move, no container is inspected, and the file is never rewritten or repaired; a runtime record that cannot bind to such state stops the scheduler with the reason, and the same state in a file no batch names stops it too. The file is opened without following a link and proven a regular file on the descriptor that is read, so a symlink, directory, FIFO or device under a state name is refused, never followed or blocked on. Written atomically after every transition; the scheduler never runs git. |
| `batches/runtime/<id>.json` | Ignored — host-local | Present only while a run of that batch is active: the `batch`, `index` and `run_id` of the running entry, the scheduler `pid` and `hostname`, `started_at`. It names no container: the one container a recovery may touch is `silverquillm-<run_id>` of the committed entry the record binds to, never a name read from the record. Written before the `running` transition, removed after the terminal one. |
| `batches/.scheduler.lock` | Ignored | The `flock` lock, holding the running scheduler's pid, host and start time. |

`silverquillm scheduler [--once] [--poll-seconds N] [--results-repo …] [--container-user …] [--replay-without-state ID]… [--acknowledge-cleanup ID]…` is the single-writer loop:

| Rule | Behavior |
| --- | --- |
| Single writer | `batches/.scheduler.lock` is held with `flock` for the scheduler's life; a second instance refuses to start and names the holder (pid, host, since). The kernel drops the lock with the process, so a crash never leaves a stale lock. One scheduler and one run container per queue, always. |
| Order | Batch files are scanned in name order; run specs are consumed in file order; one run executes at a time. At every step the scheduler takes the first due (`not_before` absent or passed), unblocked batch with an unconsumed entry, so batches execute serially in name order, an undue batch is skipped until due, and a blocked batch is skipped without disturbing the order of the rest. |
| Re-read before each run | The Nth started run of a batch is whatever the file's Nth `[[runs]]` entry is when it starts. Edits to entries already started change nothing (the state records what ran); edits to later entries, including appended ones, take effect; a file that shrinks below the cursor simply has no more work (and resumes at the cursor if entries are appended later). |
| Identity at run start | The candidate ref is resolved (absolute path, path relative to the bench repo, or a bare `candidates/` entry name) and its identity recomputed by `load_candidate_bundle` when the run starts, never at authoring time. The state records that identity and Candidate Hash; the executor runs that verified bundle, so the RunRecord carries the same recomputation. Editing a candidate between scheduling and execution is legal — results record what actually ran. |
| Execution | The bundle run path — `silverquillm.contract.drive_contract_run` over the Docker session factory — exactly what `silverquillm run --candidate` does, with the same run naming (`<benchmark>-<candidate-dir>-<timestamp>` under `runs/<candidate-dir>/`) and the same deterministic container name (`silverquillm-<run-id>`). |
| Failure continues the batch | A run that fails — an unresolvable spec (missing candidate, unknown mode or benchmark, a bundle that does not verify), a classified driver failure, or an executor exception — is recorded `failed` with its sanitized reason and the batch continues with the next entry (#66: #39 gives no abort-on-fail rule; a batch is a best-effort serial list, not a transaction). The full, credential-redacted traceback goes to the scheduler log only. |
| Missing state — replay protection | A batch file with no committed state is **blocked**: nothing from it runs, and the scheduler warns (once per file version) that starting it from entry 0 may replay runs already completed elsewhere and incur model and runtime costs. The operator restores the committed checkpoint, or acknowledges the replay for that one batch with `--replay-without-state <id>`, which creates the empty state file (commit it with the batch) and lets the batch start from run zero. The acknowledgement is batch-scoped — there is no global form — and refuses when the batch file does not exist or its state already does. Malformed or future-version state blocks the batch the same way (fail closed, nothing repaired). `queue ls` and `top` report every block. |
| Orphaned state — accounted for | Startup enumerates `batches/state/*.json` by name (plain `<id>.json`; dot-prefixed temp files are not state) beside the batch and runtime files, so committed state that no batch file names — the file was removed, or never checked out — is reconciled like any other: a running entry in it stops the scheduler before any container or executor call with the replacement-host instructions (`--acknowledge-cleanup <id>` applies to it, batch file or not); a terminal entry stays inert as the record of what ran and is never mistaken for queued work; an orphan that cannot be read — malformed, a run list the scheduler cannot have written, a symlink or special file under a state name — stops the scheduler too, because it may hide a run. `queue ls` and `top` list such state after the batches, flagged `STATE ONLY`. |
| Abandoned runs — reconciliation first | At startup, under the lock and before any new work, every run left `running` by a scheduler that died is reconciled. First — across every batch, before any container is inspected or removed — each runtime record is bound to the committed state: its batch, index and run id must equal the running entry's exactly (a record left over after a terminal transition binds to that terminal entry). A record that is unreadable, malformed or does not bind, a state with more than one running entry, and a running entry with no run id all stop the scheduler with a diagnostic, execute nothing, and keep the record for inspection by hand. Then, on the same host (the record's hostname is this one), the container `silverquillm-<run_id>` derived from the bound entry — never a name read from the record — is force-removed and its absence confirmed, the run is marked `failed` (`abandoned`) and the runtime file removed; stale metadata whose run already reached a terminal state is reconciled the same way. If the container cannot be removed or its absence cannot be confirmed (the engine is unreachable, `docker rm --force` fails, the container is still present), the scheduler **stops with a diagnostic and executes nothing** — not even another batch. Without local runtime metadata, or with metadata written on another host, the run cannot be reconciled here: the scheduler stops until the operator confirms the cleanup on the host that ran it with `--acknowledge-cleanup <id>`. |
| Cleanup acknowledgement — replacement host only | `--acknowledge-cleanup <id>` is batch-scoped and applies only when local reconciliation is impossible: this checkout holds no runtime metadata for the running entry (the state was committed elsewhere), or holds a valid record that names another host. It is refused when valid same-host metadata exists (start without the flag; the container is force-removed and confirmed gone), when the batch has no run recorded as running, and — with the runtime file kept — when the metadata is unreadable, malformed or does not bind to the recorded run. Once permitted, the run is marked `failed` (`abandoned`) on the operator's word and the batch continues. |
| Signals | SIGINT and SIGTERM interrupt the run in flight: its container is force-removed and confirmed gone, the entry is recorded `failed` (`interrupted`), the runtime file removed, and the scheduler unwinds; if the container cannot be confirmed gone, the entry stays `running` with its runtime metadata and the next startup reconciles it. SIGKILL cannot be caught: it leaves exactly that state for the next startup. |
| Replacement and restore | A fresh checkout with committed state resumes every batch at its recorded cursor. Replacement safety is limited to the latest committed checkpoint: commit `batches/state/` after each run or completed batch. A checkpoint that records a run as `running` fails closed on the new host until `--acknowledge-cleanup`. |

`silverquillm queue ls` prints a one-shot table — every batch, its `not_before` and whether it is due, per-run specs and states (started runs from the state file, pending ones from the file), malformed files, every block (missing state with the replay warning and the acknowledgement command, unreadable state, an abandoned run), committed state no batch file names (listed after the batches, flagged `STATE ONLY`, its entries the record of what ran and never pending work) and whether a scheduler holds the lock. `silverquillm top [--interval N]` redraws the same view in the alternate screen until `q`. Both are read-only and show nothing host-local beyond the lock holder; editing stays `$EDITOR`-native on batch files.

### Publishing — a porter with two checks, never a librarian

`scripts/publish_results.py --results-repo <clone> --dest published/<subdir> RUN_ID… [--candidates-dir DIR] [--allow-invalid] [--dry-run]` copies the named Run Records (`manifest.json` + `scores.json`, byte for byte) from the private Results Repo into the destination. It never commits: the operator reviews the published diff and commits, and that commit is the approval stamp.

| Check | Outcome |
| --- | --- |
| Traceability | **Hard refusal.** The run's candidate identity must exist under `candidates/` as `<slug>--<hash8>` and verify by recomputation: the checked-in bundle is ingested and its Candidate Hash and identity triple must equal the record's. An absent candidate ("promote it first"), a bundle that fails verification, an identity mismatch (both values printed), or a `legacy` identity (which has no bundle) refuses. When the Results Repo holds the vendored copy at `results/<hash>/candidate/` it is re-verified too. **The candidate is what the tree holds:** the `<slug>--<hash8>` wrapper and its `bundle/` must be real directories by `lstat`, resolving in place under `candidates/`; a symlink under a candidate name — even one pointing at a valid bundle elsewhere on the host — is a hard refusal, never followed, because the run would be traced to content outside the repository. The source Run Record is proven through every ancestor: the Results Repo's `results/` directory, the candidate-hash directory and the run directory must be real directories by `lstat` and `manifest.json` and `scores.json` regular files — a record reached through a symlinked ancestor is never publishable, however valid its target — and the complete proof is repeated immediately before each copy, so a substitution after planning is refused and rolled back. |
| Validity | **Warning.** `leaderboard_valid: false` — a Resume Leg, an ineligible benchmark, an unevaluated or gate-failed run — is reported with its reasons and refuses unless `--allow-invalid` is passed. A published-but-invalid record carries the flag, and leaderboard tooling filters on it mechanically, so it can never contaminate a leaderboard. |

Publication is a **transaction** on disk, not only in the plan:

| Phase | Rule |
| --- | --- |
| Serialization | One invocation per destination: recovery, planning, staging, commit, finish and rollback run under an exclusive per-destination lock — an advisory `flock` on the destination directory itself (`PublicationLock`), which leaves no artifact under the destination or in the operator's commit and is never inferred from a recorded pid or hostname (a reused pid or a copied file could fake one). A second live invocation refuses (`REFUSED: another publication invocation holds …`, exit 1) rather than recover a journal that belongs to a transaction still in flight; the kernel drops the lock when the holder exits, so the next invocation then recovers whatever journal it left. A live transaction and a stale journal therefore never look alike: the first holds the lock, the second cannot. Within one process the phases re-enter one hold. The lock creates an absent destination — and any missing ancestor — for the lifecycle and, when the invocation published nothing into it, removes exactly those again on release, each only on proof (`silverquillm.created_directories`): created descriptor-first under a private name and placed with a no-replace rename under an advisory `flock` on its parent directory, so the identity never comes from a pathname and a directory that appears under the name meanwhile is someone else's, used as found and never removed; removed only while proven, under that same lock, still to be the very directory created and empty, and through a private name again, so the one deletion is of a name nobody else knows and a replacement caught in that instant is moved back and kept. The destination is locked through a duplicate of the descriptor the creation handed over, under the same parent lock, so the directory locked is the directory created, and every failure after the destination was created — opening or locking it, a holder already on it, inspecting it — unwinds the same way before its refusal (exit 1) is reported. What is not restored — a directory that cannot be inspected or removed, a replacement, content something else wrote there, a moved-aside entry that cannot be moved back — is a `PublicationCleanupError` (`CLEANUP FAILED …`, exit 2, the refusal still printed) naming the kept path: a refusal over residue is never reported as clean. The parent-directory lock serializes every promote and publish invocation and is what closes both instants against them; on a platform without `RENAME_NOREPLACE` the placement is a plain rename, safe under that lock alone. A destination that received records is kept, and so is one holding the journal a recovery error retains. |
| Plan | Every run is checked before the first byte is written (all or nothing). A byte-identical record already at the destination is skipped — but only a real directory holding both record files as regular files (by `lstat`) can be recognized as already published; a symlinked record directory or record file, even one resolving to identical bytes, refuses. A differing record is a conflict that refuses — a published record is never overwritten. A pending journal under the destination refuses planning until recovery runs. |
| Dry run | `--dry-run` is strictly read-only and takes a *shared* hold of the destination lock, so a transaction in flight is reported as in flight (`REFUSED … in flight … the dry run changed nothing`, exit 1) — never as an interrupted one awaiting recovery — and an absent destination is never created. It never recovers: a pending journal is inspected, the recovery that would occur is reported (`RECOVERY REQUIRED …`, naming the directories a rollback would remove or that a completion would leave in place), and the exit status is nonzero; journal, staging tree, records, bytes and mtimes stay exactly as they were. |
| Stage | New records are copied into a private staging directory beside the destination (`<dest>/.publish-staging-<nonce>/`), then re-read: each copy must be byte identical to its source and re-prove as the same Run Record. The journal `<dest>/.publish-journal.json` is created first (exclusively — a concurrent publication into the same destination refuses) and names exactly the directories this invocation will create. Beginning is all-or-nothing: once the journal exists, every failure — duplicating its descriptor (the process out of descriptors), writing it, closing either descriptor, creating staging — is an initialization failure that removes what the attempt created (the staging directory, then the journal) and refuses with the cause chained (`REFUSED: cannot begin …`, exit 1, never a traceback), leaving no journal, no staging directory and no destination the invocation created. The journal is removed only once proven to be the very file this attempt made: a regular file with the created file's device and inode, and — while a descriptor of that file is still open — still linked by that descriptor's own link count, so a replacement that reuses the freed inode is caught; when closing the last descriptor was itself the failure, the entry must instead read back, through a no-follow descriptor of that inode, as exactly the bytes the attempt wrote. Every descriptor is closed on every path. A removal that itself fails keeps the evidence and raises a recovery error (exit 2) that names what is retained — the journal, and the staging directory when it is the one that could not go — says what the journal plans and how the next invocation recovers it if it parses, and says to inspect and delete it by hand if the write was interrupted. A journal replaced under the attempt's name is never removed. A failure while finishing, after every record was committed, keeps the complete journal for the next invocation to finish and says so. |
| Commit | Only after every staged record is complete, one atomic rename per record directory, each journaled before and after. A destination that appeared meanwhile refuses. |
| Finish | The staging directory and the journal are removed; the success summary (the `A <path>` lines and the commit reminder) prints only now. |
| Rollback | A failure at any copy, validation or rename step removes every final directory this transaction created (only names the journal lists), the staging directory and the journal; pre-existing records are never touched. A rollback that itself fails is reported prominently, the journal stays, and no publication into that destination proceeds until recovery succeeds. |
| Recovery | Recovery runs under the destination lock, so it only ever sees a journal whose transaction has exited — a live one holds the lock and refuses this invocation first. The journal itself is an untrusted filesystem boundary: it is opened without following a link (a symlinked journal — dangling, or pointing at a valid-looking journal elsewhere — is refused, never read), proven a regular file by `fstat` on the very descriptor that is then read, and a directory, FIFO, socket or device under its name is refused explicitly; recovery derives no deletion authority from anything but a real in-tree regular file, and the read-only inspection refuses the same way. The next invocation reads the journal before planning: a transaction that had committed every record is completed (staging and journal removed); anything less is rolled back, including a rename that landed before the journal could record it. Recovery removes only what the journal proves the transaction created: the journal is trusted in the exact form the script writes it — every name one plain child-name component (the staging name in its generated format; no separator, `.`/`..`, absolute path, unexpected or missing field, repeated name, or a `committing` entry that is not planned or is already committed) — and every cleanup target is proven, before anything is removed, to be a real directory that resolves to an immediate child of the destination and holds only what the transaction copies: `manifest.json` and `scores.json` as regular files by `lstat`, so a directory (which could hold anything), a symlink, a FIFO, a socket or a device under either name is refused. A record still in staging may hold a subset of the two, because the process can die between the copies; a committed record, or one whose rename landed while `committing` named it, must hold both. A symlink anywhere is refused, never followed, and the complete target set is validated before the first removal. A journal that fails any check is a recovery error that leaves every byte, name and mtime under the destination unchanged and the journal in place. |

Discovery of published results goes through manifests only, never a path convention: a directory anywhere under `published/` is a published run iff it holds `manifest.json` beside `scores.json` and the pair re-proves as a Run Record whose `run_id` is the directory's name (`publish_results.iter_published_records`); dot-prefixed directories (staging) are never records. Published records are real in-tree directories holding regular files: discovery never follows a symlinked directory and refuses a symlink or special file under a record file's name, so a published record is always the bytes the repository holds. How `published/` is organized — per blog post, per experiment — is the operator's, by hand.

### What stays manual

- Completing the promoted README (what the candidate varies, where the base digest came from, optionally a safe Config Repo revision) and committing the directory.
- Authoring and editing batch files; deciding when a batch is due; acknowledging a batch that starts without committed state.
- Committing `batches/state/` checkpoints after each run or completed batch, and confirming a remote run's cleanup on a replacement host.
- Choosing which runs to publish, the destination, and committing the published files.
- Leaderboard and aggregate derivation over `published/` is future work; whatever derives it filters on `leaderboard_valid`.
